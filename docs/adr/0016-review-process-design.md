# ADR-0016：评审交互设计——无卡顿模式 + A3 混合批量操作

## 状态

已接受（2026-07-25，产品负责人确认；同日被 ADR-0022 修订：评审由两态改为三态——待定/保留/剔除，导出确认弹窗增加封账提示与待定项报数；两态相关表述以 ADR-0022 为准）

## 背景

v1.x 存在多套入口混用的情况导致体验混乱，且评审操作每次都要等待网络请求与数据库落盘，导致界面卡顿。V2 需要统一"日常预览"的打开方式，同时实现评审操作的即时响应。

## 决定

### 评审流程总览

评审分为**三个明确阶段**：

```
阶段一：评审模式
 ├─ 可反复切换抽屉、勾选/剔除候选
 ├─ 所有操作只改内存状态
 └─ 可随时暂停、保存项目、退出再回来继续

 ↓ [点"[导出地基]"]

阶段二：导出确认（F2）
 - 弹窗汇总："本次将导出建筑 80、道路 75..."
 - 可检查、可取消返回评审
 - 一旦点"[确认]" → 评审结束

 ↓ [点"[确认]"]

阶段三：后台导出（G2）
 - 非阻塞式进度条反馈："📦 导出中 (45%)..."
 - 评审不再打开
 - 完成 → 自动跳转下一阶段（生成地基）
```

### 界面布局

采用 **左侧卡片列表 + 中间地图 + 右侧信息面板** 的三栏布局：

```
┌──────────────────────┬──────────────────────┬──────────────────────┐
│   类别标签           │                      │  当前选中项详情       │
│  [建筑 (120)]        │      大地图区域        │  ○ 教学楼            │
│  [道路 (95)]         │                      │  building=commercial │
│  [水域 (42)]         │                      │  ☑ 保留 / ☐ 剔除     │
│  ...                 │                      │                      │
├──────────────────────┤                      ├──────────────────────┤
│ ✓ 已选：3 项          │                      │  下一步提示文字       │
│ [全选] [取消全选]    │                      │                      │
├──────────────────────┤                      └──────────────────────┘
│ ☑ ○ 体育馆           │
│ ☐ ○ 游泳池           │
│ ☐ ○ 校门             │
└──────────────────────┘
```

### 交互规则

| 条件 | 系统行为 |
|------|---------|
| **未勾选或勾选 1 个** | 不显示"[全选] [取消全选]"按钮 |
| **勾选 ≥2 个** | 顶部**自动浮现**"[全选] [取消全选]"两个按钮 |
| **点击卡片前的复选框** | 立即响应（内存操作，无 UI 延迟） |
| **点击地图上的对象** | 高亮对应卡片 + 反之高亮 |
| **批量操作触发** | 点"[全选]" → 本类所有卡片勾选<br>点"[取消全选]" → 本类所有卡片取消 |

### 数据分类与去留逻辑

#### 采集时的自动分类

系统在高德地图/Overture 上查到候选对象后，按以下规则分流：

- **标签明确匹配五大类**（建筑/道路/水域/植被/体育）→ 进入对应抽屉，只有**保留**或**剔除**两个选项（注：ADR-0022 已修订为三态：待定/保留/剔除，待定为初始态）
- **标签无法归入五大类** → 直接进入"**其他**"抽屉（无需手动标记，自动收录）

#### "剔除"的实际效果

| 操作 | 效果 | 数据去向 |
|------|------|---------|
| **保留** | 纳入最终导出 | 在导出时刻写入 SQLite，生成 MC 方块 |
| **剔除** | **永久排除** | 直接丢弃，不占用存储（无回收站机制） |
| **其他类别** | 单独管理 | 自动收录非五大类对象（如校内铁路、雕塑等） |

### 批量删除确认规则

| 单次操作数量 | 确认策略 |
|-------------|---------|
| **1-4 项** | 直接执行，无弹窗 |
| **≥5 项** | 二次确认弹窗："确定删除这 N 项吗？" |

### 性能优化原则

- **评审操作只改内存状态** —— 不写盘、不等待网络
- **真正落盘发生在导出时刻** —— 一次性批量写入
- **界面响应永远即时** —— 无论列表多长都不卡

### 导出时的反馈机制（G2）

导出确认后，采用**非阻塞式进度条**：

- 弹窗消失，主界面右上角出现浮动提示："📦 导出中 (45%)..."
- 您可看到进度变化，但评审入口已禁用
- 完成后自动跳转至"生成地基"阶段

---

## 原因

1. **解决 v1.x 卡顿痛点**：评审时每个候选都需要同步落盘和网络请求，导致明显延迟；
2. **提升效率**：批量操作减少重复点击，尤其是处理大量候选对象时；
3. **防止误操作**：删除≥5 项才弹窗确认，平衡速度与安全性；
4. **清晰阶段划分**：评审模式 vs 导出模式的界限分明，避免混淆；
5. **符合用户审美**：采用 v1.x 已有的三栏布局风格，降低学习成本。

## 后果

- **开发复杂度增加**：需要实现内存缓冲层 + 批量落盘机制；
- **导出时间变长**：从原来逐步落盘变为一次全量落盘；
- **不可逆性强**：剔除非正式式删除，无软删除机制；
- **用户体验提升**：评审过程流畅，无卡顿感。
